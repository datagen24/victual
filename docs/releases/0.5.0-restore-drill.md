# 0.5.0 backup and restore drill

Run date: 2026-10-20, issue [#1010](https://github.com/datagen24/victual/issues/1010), release
gate R5. The drill followed [Backup and restore](../manual/operator/backup-restore.md) against
the **published v0.5.0 images**, on a disposable PostgreSQL. No production database exists to
drill against, and none was used.

The script and the evidence it wrote are in
[`.devtools/pgsql/restore-drill/v0.5.0/`](../../.devtools/pgsql/restore-drill/v0.5.0/). To
repeat it, pull the three images by the digests below and run:

```bash
.devtools/pgsql/restore-drill/v0.5.0/drill.sh <output directory>
```

## The source

The v0.5.0 pod migrated and seeded a new database, `victual_source`, to migration 318. The
artifact's own code then wrote the data:

- **Bookings:** v0.5.0's `.devtools/pgsql/ledger-generator.php`, run with the migrate image's
  PHP as `victual_migrate`, with `--products=25 --days=120 --seed=1010 --reconcile`. It made
  685 `stock_log` rows, 142 `stock` rows and 46 `stock_entry_origins` rows. They include 42
  edits and 22 undone bookings, and nothing was refused.
- **Files:** three random-byte userfiles of 40,123, 80,123 and 120,123 bytes, uploaded
  through `PUT /api/files/userfiles/{name}` with an administrator's API key. The source held
  each one byte for byte before the dump.

Across its 89 tables the source had 2,348 rows.

## Dump

`pg_dump -Fc` as **`victual_app`**, the application role, as the manual's backup command
reads in the two-role deployment. It exited 0 in 0.2 s and wrote a 1,434,187-byte dump.

## Restore

Each attempt restored into a new empty database with `pg_restore --exit-on-error`:

| Attempt | Exit | First error |
|---|---|---|
| As `victual_app`, no `roles.sql` (the manual as written, with `<DB_USER>` the app role) | 1 | `must be owner of schema public` at `ALTER SCHEMA public OWNER TO victual_migrate` |
| As `victual_migrate`, no `roles.sql` | 1 | The same |
| As `victual_app`, after `roles.sql` | 1 | `permission denied for schema public` at `CREATE COLLATION public.nocase` |
| **As `victual_migrate`, after `roles.sql`** | **0** | None |

The manual as written does not restore this deployment, for two reasons. The roles are
server-wide and are not in a dump. And the dump gives the `public` schema to
`victual_migrate`, which only `roles.sql` prepares the empty database for. The working
sequence is `roles.sql` against the empty database, then `pg_restore` as `victual_migrate`.
It took 1.0 s. The manual now says so, in the same pull request as this record.

## Migrator on the restore

The v0.5.0 migrate image ran against the restored database as `victual_migrate`, with
`VICTUAL_BOOTSTRAP_ADMIN_PASSWORD` set as the pod's Secret forces. It exited 0 in 0.9 s and
printed `Schema is up to date at migration 318.` The schema and data dumps taken before and
after it are identical, so it changed nothing. Restoring did not reset the administrator's
password either: the seeder only runs when the migrator creates the schema.

| SHA-256 of each stored file | Identical, and equal to the uploaded bytes |

The data dump is compared with its lines sorted. `pg_dump` orders the tables that share
circular foreign keys (`label_templates` and `label_template_versions`, and three other
cycles, one of them a table that references itself) by object id. A restore renumbers object ids, so the unsorted dumps differ only in
the order of whole table sections.

## The restored instance serves

The same pod, pointed at the restored database:

- served each of the three userfiles through `GET /api/files/userfiles/{name}`, byte for byte
  as uploaded;
- booked a purchase of 3 of product 1 through `POST /api/stock/products/1/add`, taking its
  stock from 6 to 9. The purchase's booking got id 686, after the restored maximum of 685, so
  identity sequences continue rather than collide;
- undid it through `POST /api/stock/transactions/{id}/undo`, which returned the stock to 6.

## Not covered

- **`FILE_STORAGE` `filesystem`.** The drill ran on database storage only, so the manual's
  storage-directory step was not exercised. The pod spec and the configuration reference
  recommend database storage for this deployment.
- **Labels, MQTT and InfluxDB.** The source had no label printers, label jobs or outbox
  traffic, and the pod ran without MQTT or InfluxDB. Their tables were restored and compared
  as rows, but nothing exercised them afterwards.
- **A restore across versions,** for example a 0.4.4 dump restored under 0.5.0. That is a
  restore followed by an upgrade, and the
  [0.5.0 upgrade rehearsal](0.5.0-upgrade-rehearsal.md) covers the upgrade half.
- **Scale.** 2,348 rows; the timings above are for that size only.

## Observed in passing

An upload sent with curl's default `application/x-www-form-urlencoded` content type, not
the documented `application/octet-stream`, stored an **empty** file and still answered 204.
The framework parses a form body before the controller reads the request stream, so storage
receives a stream that is already at its end. The drill's first run did this. The script now
sends the documented type and refuses to continue unless the source holds the uploaded bytes.
This behaviour is outside the restore claim and is not changed here.
