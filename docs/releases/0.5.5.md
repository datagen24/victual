# Victual 0.5.5

**Tag `v0.5.5`, on `master` at the commit that merges this record.** It follows
[0.5.4](0.5.4.md). It is an interim patch release cut from the 0.6.0 list. It holds:
- the label printing work finished since 0.5.4;
- fixes for the MCP sidecar limitations that 0.5.4's dev conversations found;
- a few small enhancements;
- design records that 0.6.0 builds on.

It adds one migration, a database function with no callers. One behaviour changes, for label
print jobs whose printer has been deactivated (see Compatibility). The plan and its decisions
are in [release-planning/2026-10-24](../../release-planning/2026-10-24/dashboard.md).

## What changed

| Change | Effect for an operator or client |
|---|---|
| A deactivated printer's queued label jobs stay queued ([PR 1105](https://github.com/datagen24/victual/pull/1105)), as decided in [ADR-0053](../adr/0053-label-print-jobs-stay-queued-while-a-printer-is-inactive-and-reprint-stays-the-recovery.md) ([PRs 1095](https://github.com/datagen24/victual/pull/1095) and [1107](https://github.com/datagen24/victual/pull/1107)). | Deactivating a printer, for example to change a roll, no longer dead-letters its queue at the worker's next claim. ## Database migrations

One: `0319.pgsql.sql` creates `victual_barcode_canonicalize`, an `IMMUTABLE` function that
creates and reads no table. 0.5.5 expects the schema 0.5.4 left (migration 318), plus this
function.

## Compatibility

- **Label queue:** a queued job whose printer is deactivated now stays queued. Before, it was
  dead-lettered at the worker's next claim. The REST API is unchanged. `GET /api/labels/jobs`
  shows such a job as `queued` and does not say why it does not move; the printer's `active`
  flag does. An operator who relied on deactivation to abandon a queue should delete the
  printer instead.
- **System config:** `GET /api/system/config` gains the installation country. The field is
  additive.
- **Sidecar tools:** `all-read` gains `recent_transactions`. `set_due_date` stays off until
  `mcp.enabledTools` names it or enables `stock-write`. `list_locations` now returns at most
  50 rows unless `limit` asks for more, and reports `total`.
- **Victual image:** apart from the above, the REST API, permissions and schema are as in
  0.5.4.

## Known limitations

- **A dead-lettered label job does not say why.** The reason exists in the outbox, but
  `GET /api/labels/jobs` does not return it. Issue 1102 (0.6.0) adds it.
- **The restore drill was not repeated.** The v0.5.0 drill carried over to later releases only
  while they added no migration. 0.5.5 adds one function-only migration.
