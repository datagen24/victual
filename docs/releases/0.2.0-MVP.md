# Victual 0.2.0-MVP

**Tag `v0.2.0-MVP`, 2026-09-24, on `master` at the commit that merges this record.** It
follows [0.1.0-MVP](0.1.0-MVP.md). [0.1.1-MVP](0.1.1-MVP.md) was recorded and merged
([PR 223](https://github.com/datagen24/victual/pull/223)), but its tag was never placed.
Its changes are in this release, and no `v0.1.1-MVP` tag will be placed.

This is a minor version because it adds a migration, changes responses a client can see,
and refuses input that 0.1.0-MVP accepted. It is also the first release whose images
`.github/workflows/release.yml` publishes to GHCR
([ADR-0030](../adr/0030-released-images-are-published-to-ghcr.md), Proposed).

## What changed

The 0.1.1-MVP record lists its own changes: label writes go through the transaction layer
and advance the changed time, and a PostgreSQL server older than 15 is refused at
startup. The table below lists what landed after it.

| Change | Effect for an operator or client |
|---|---|
| Migration 0288 adds a foreign key from `stock.location_id` to `locations.id` ([ADR-0029](../adr/0029-stock-locations-reference-existing-locations.md), [PR 477](https://github.com/datagen24/victual/pull/477)). | **An upgrade can stop.** If any stock row names a location that no longer exists, the migration refuses. It names sample rows and changes nothing; see [Repairing stock location references](../manual/operator/updating-migrations.md#repairing-stock-location-references). Deleting a location that still holds stock now answers 400. |
| `Content-Type: application/json; charset=utf-8` is accepted on writes ([PR 234](https://github.com/datagen24/victual/pull/234), #229). | Before, every write that sent a charset parameter was answered `400 Bad Content-Type`. |
| Eleven fields the API document types as booleans are sent as booleans (PR 234, #230). | A client that parsed them as the integers `0` and `1` must accept `true` and `false`. [ADR-0027](../adr/0027-timestamps-are-local-strings-documented-booleans-are-booleans.md) (Proposed) records which side moved. |
| `tracked_time` on chore execution and battery charge, and `done_time` on task completion, accept RFC 3339 and refuse what they cannot read ([PR 235](https://github.com/datagen24/victual/pull/235), [ADR-0028](../adr/0028-a-timestamp-a-write-route-cannot-read-is-refused.md), Proposed). | Before, any value that was not exactly `Y-m-d H:i:s` was ignored, and the route booked the current time and answered 200. Now it answers 400. |
| Stock bookings of the same product are serialised with a transaction-scoped advisory lock ([PR 471](https://github.com/datagen24/victual/pull/471), #458). | Concurrent bookings of one product no longer read stale amounts. A booking can wait for another to commit. |
| Undo fixes: a compacted purchase subtracts only its own amount ([PR 469](https://github.com/datagen24/victual/pull/469)); an undo that a later uncorrelated booking depends on is refused ([PR 442](https://github.com/datagen24/victual/pull/442)). | Undo no longer removes more stock than the booking added, and no longer leaves later bookings inconsistent. |
| Barcode lookup: one fetch path with a host policy that refuses loopback, private, link-local and metadata addresses, no redirects, 5 s and 10 s timeouts and a 10 MiB cap; picture file names and extensions are held to allow-lists ([PRs 472](https://github.com/datagen24/victual/pull/472), [473](https://github.com/datagen24/victual/pull/473); security sweep S14 closed). | A barcode source can no longer make the server request an internal address or store a non-image file. A picture that fails a check is skipped, and the product is still created. |
| Reverse-proxy authentication refusals answer 401 or 403 with a generic body ([PR 445](https://github.com/datagen24/victual/pull/445)). | Before, they answered 500 with a body naming the configuration setting. The detail now goes to the server log. |
| Client errors on several paths answer 400 or 404 where they answered 500 ([PRs 450](https://github.com/datagen24/victual/pull/450), [451](https://github.com/datagen24/victual/pull/451), [466](https://github.com/datagen24/victual/pull/466), and others from the bug sweep merged as PRs 442–456). | A client sees a refusal in the documented error envelope and no server fault. |
| Label geometry that a printer cannot represent is refused at registration ([PR 468](https://github.com/datagen24/victual/pull/468)); MQTT publication failures stay inside the request's no-throw contract ([PRs 449](https://github.com/datagen24/victual/pull/449), [467](https://github.com/datagen24/victual/pull/467)). | A broker failure no longer turns a completed write into an error response. |
| The label worker is a `CronJob` in every deployment manifest ([PR 227](https://github.com/datagen24/victual/pull/227)). | A drained queue no longer puts the worker into restart backoff. |
| `WebhookRunner` is deleted ([PR 474](https://github.com/datagen24/victual/pull/474)). | None. Nothing called it after plan 32 removed the label webhook. |
| `deploy/k3s/` names `ghcr.io/datagen24/victual-*:0.2.0-MVP`; `deploy/kind/` maps those names back to local builds. | A k3s node pulls the release. The podman and compose manifests still name `localhost/` images. |

## Open verification and known limitations

These are unchanged from [0.1.0-MVP](0.1.0-MVP.md#open-verification): the household cluster
apply, a label worker image reaching the printer from a cluster, Home Assistant surviving
the pod at zero, and the MCP replay tests. 0.1.1-MVP added one: the renderer's HTTP
routes have no scripted test. This release adds two more:

- The arm64 images have never been booted outside the release workflow.
- The parity suite has not been run since 0.1.0-MVP.

## Installing and upgrading

Images are `ghcr.io/datagen24/victual-{app,web,migrate,label-renderer,label-worker,mcp}:0.2.0-MVP`
for `linux/amd64` and `linux/arm64`. The GitHub release lists each image by digest.

From 0.1.0-MVP, pull the new images and restart. `bin/victual-migrate` applies 0288. If
it refuses, repair the stock rows it names and run it again. The database server must be
PostgreSQL 15 or newer.
