# Victual 0.3.1

**Tag `v0.3.1`, on `master` at the commit that merges this record.** It follows
[0.3.0](0.3.0.md). It is a patch version because it adds no migration and changes no
application code, no route and nothing on the wire. What it changes is how Victual is
deployed. It is the first release that publishes the Helm chart
([ADR-0038](../adr/0038-kubernetes-deployments-ship-as-a-helm-chart.md), Proposed), and
that publication is ADR-0038's acceptance prerequisite 5.

## What changed

The release spans PRs 672–685, 42 commits.

| Change | Effect for an operator |
|---|---|
| **The Kubernetes deployment is a Helm chart**, `deploy/helm/victual/` ([PR 680](https://github.com/datagen24/victual/pull/680)). `deploy/k3s/*.yaml` is now its rendering, and `deploy/production/` is gone. | Deploy from `oci://ghcr.io/datagen24/charts/victual` with a values file started from [`values.example.yaml`](../../deploy/helm/victual/values.example.yaml). Its schema refuses a missing value or a `CHANGE-ME` placeholder by field name. Anyone using `deploy/production/`'s `values.yaml` moves to the chart: drop `cluster:` (use `--namespace` and `--kube-context`) and move each `secrets.onepassword.*Item` to `secrets.onepassword.items.*`. `kubectl apply -k deploy/k3s` still works, with the same objects as 0.3.0 apart from the image tags. |
| **Upgrade hooks** ([PR 681](https://github.com/datagen24/victual/pull/681), ADR-0038 decision 9). | Under Helm, a `pre-upgrade` Job runs `bin/victual-timestamp-preflight`, so a database that a migration would refuse fails `helm upgrade` before any pod is replaced. With MQTT enabled, a `post-install`/`post-upgrade` Job runs `bin/victual-publish-state`. `kubectl apply` runs neither. |
| **`/opt/victual/php` in the app and migrate images** (PR 681). | The interpreter now has a fixed path, which is how the hook Jobs run a `bin/` command from the image. **The 0.3.1 chart's hooks need 0.3.1 images**, so don't point `image.tag` at an older release. |
| **`helm rollback` is no recovery after a migration** ([PR 682](https://github.com/datagen24/victual/pull/682)). | Measured on kind: after an upgrade that migrated, the older pod never becomes ready. Restore the backup instead. See [Updating and migrations](../manual/operator/updating-migrations.md). |
| **One Secret per credential** ([PR 679](https://github.com/datagen24/victual/pull/679), plan 36). | The database Secrets hold only the database credential. The bootstrap admin password, the MQTT password and the InfluxDB token each have their own Secret. An existing 1Password deployment moves its values first: [deploy/README.md, "One Secret per credential"](../../deploy/README.md#one-secret-per-credential). |
| **`roles.sql` takes passwords from the environment** and keeps them out of server logs and statistics ([PR 674](https://github.com/datagen24/victual/pull/674), [PR 676](https://github.com/datagen24/victual/pull/676)). | Export `MIGRATE_PASSWORD` and `APP_PASSWORD` before `psql -f roles.sql`. The script refuses `-v` arguments. |
| **kind and talos install through the chart** ([PR 685](https://github.com/datagen24/victual/pull/685)). | `deploy/kind/up.sh` and `deploy/talos/up.sh` run `helm upgrade --install` with their own values files. talos installs the published chart by version and needs `KUBE_CONTEXT`. |
| **The release workflow publishes the chart** ([PR 684](https://github.com/datagen24/victual/pull/684)). | A tag whose `Chart.yaml` disagrees with `version.json` is refused, and the GitHub release names the chart's reference and digest. |

## Open verification and known limitations

- ADR-0038 prerequisite 5 is met. Talos deployment was deferred because the production
  configuration uses InfluxDB 1.x and the writer supported 2.x. Release 0.3.2 adds 1.x
  support, but the maintainer had not tested it on 2026-10-09. Prerequisite 6 remains
  unmet. Accepting the record is its own pull request.
- The 0.3.0 limits stand: the household cluster has not run on live data; a label worker
  image has not reached the printer from a cluster; the Home Assistant checks and the MCP
  replay tests are outstanding; and migration 0301 has no reverse.
- Credential rotation (plan 36) is designed but not built. Rotating a password is still a
  manual `roles.sql` run plus a pod restart.

## Installing and upgrading

Images are `ghcr.io/datagen24/victual-{app,web,migrate,label-renderer,label-worker,mcp}:0.3.1`
for `linux/amd64` and `linux/arm64`. The chart is
`oci://ghcr.io/datagen24/charts/victual`, version 0.3.1.

From 0.3.0, no migration runs. On Kubernetes with Helm:

```bash
helm upgrade --install victual oci://ghcr.io/datagen24/charts/victual --version 0.3.1 \
  -f values.yaml --namespace victual --create-namespace --wait --timeout 10m
```

Before the first install over a deployment that `deploy/production/` or a kustomize overlay
applied, move the Secrets to the one-per-credential layout first. Then pass
`--take-ownership` to that first `helm upgrade --install`, so Helm adopts the objects it did
not create instead of refusing them. `deploy/kind/up.sh` does this. Under podman or
Compose, pull the 0.3.1 images and restart.
