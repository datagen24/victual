# Victual 0.5.2

**Tag `v0.5.2`, on `master` at the commit that merges this record.** It follows
[0.5.1](0.5.1.md). It is a patch release, and the reason to install it is security. 0.5.2 raises the
PHP floor and rebuilds every image on PHP 8.5.12, the fixed release for PHP2Shell. It also closes
an account-existence oracle in medication-preset sharing, and makes four interim quality-of-life
changes. The [0.5.2 release dashboard](../../release-planning/2026-10-21/dashboard.md) tracks its
eight issues, all closed.

## Security

- **PHP2Shell** (GHSA-w8hw-w9fx-j79w and GHSA-6wmf-4rv5-p3rp, CVE-2026-109618 and CVE-2026-109619).
  - **The flaw:** unauthenticated remote code execution in PHP core, caused by request state that
    is corrupted during bailout and cleanup. It affects every web-serving SAPI, including PHP-FPM,
    which serves Victual's app image.
  - **Affected:** the v0.5.0 and v0.5.1 images run PHP 8.5.10.
  - **Fixed:** the v0.5.2 images run PHP 8.5.12, through the nixpkgs input locked to `a5fc1be5`.
  - **What an operator should do:** update to 0.5.2. A deployment that runs Victual on its own PHP
    must update PHP to 8.4.27 or 8.5.12 first. 0.5.2 refuses to start on an earlier release of
    either branch.
  - Recorded as #1043 and decision D9; shipped in [PR 1045](https://github.com/datagen24/victual/pull/1045).
- **Medication-preset sharing no longer reveals which accounts exist** (#737, decision D3).
  - **Before:** a caller who held a share could learn three things. A share request answered `422`
    for an unknown user and `204` for a real one. A request against a share they could not see
    answered `403`. A removal of such a share answered `403` rather than `404`.
  - **Now:** each of those answers the same way whether or not the user or share exists. See
    Compatibility.
  - Shipped in [PR 1050](https://github.com/datagen24/victual/pull/1050) and
    [PR 1051](https://github.com/datagen24/victual/pull/1051).

## Database migrations

None. Nothing under `migrations/` or `db/` changed since `v0.5.1`. 0.5.2 expects the schema 0.5.1
left, at migration 318.

## Compatibility

- **PHP:** an installation on PHP 8.4.1 to 8.4.26 or 8.5.0 to 8.5.11 is refused at startup until PHP
  is updated. The released images already ship 8.5.12.
- **Share requests** (`/consumptionrecipes/{recipeId}/shares`):
  - `POST` and `PUT` no longer answer `422 invalid_user`. An unknown or unshareable target answers
    `204` and writes nothing.
  - A `POST` with neither `user_id` nor `username` answers `400 invalid_request` instead of `422`.
  - `DELETE` of a share the caller may not remove answers `404 not_found` instead of `403`.
  - A client that relied on `422` to detect a typo should read the share list after sharing.
- **Unencodable responses:** a route whose body could not be encoded now answers a JSON `500`
  instead of an empty body. A write inside a request transaction is rolled back rather than
  committed.
- **File uploads:** a body sent as JSON, form-urlencoded, XML or multipart answers `415` and stores
  nothing, where it used to store an empty file. Clients that send `application/octet-stream`, a
  file's own type, or no type are unaffected.
- **Images, chart values and manifests** change in their version and in the PHP release they carry.
  Deployment paths, configuration and permissions are unchanged.

## Known limitations

- **The PHP floor is enforced at HTTP startup only.** `public/index.php` runs the check. The `bin/`
  commands, such as `victual-migrate`, do not. PHP2Shell is reachable only through the web SAPIs,
  and the composer constraint still applies to an installation that composer manages.
- **Direct `json_encode` writes remain** in the web manifest, the path-parameter refusal, one
  authentication refusal and the recipe page script. They can still produce an empty body on an
  encode failure. They are issue 1047 (0.6.0).
- **The medication sidebar test cannot tell one visible child from three.** All three children
  share `STOCK_VIEW`.
- **Restore drill scope** is unchanged from 0.5.1: only `FILE_STORAGE` `database` was drilled.
- **Gate R6** (a production support claim for cluster labels and shutdown) stays unplaced. 0.5.2
  makes no cluster label or shutdown support claim.
