# Victual 0.4.2

This is the release candidate record for `v0.4.2`. The tag has not been placed.
It follows [0.4.1-hotfix1](0.4.1-hotfix1.md). The final merge commit and its checks
must be recorded before the maintainer places the signed tag.

## What changed

| Change | Effect for an operator or client |
|---|---|
| Release evidence ([PR 961](https://github.com/datagen24/victual/pull/961)) | Corrects the historical 0.4.1 and hotfix records. It preserves their tags and distinguishes post-tag checks from checks run before release. |
| Domain view permissions ([PR 962](https://github.com/datagen24/victual/pull/962), issue 913) | Documents battery, calendar and equipment read permissions, inheritance and the calendar sharing-link exception. Grants and authorization behavior do not change. |
| API contract ([PR 963](https://github.com/datagen24/victual/pull/963), issues 801, 893, 936 and 953) | Documents existing stock label modes, fractional chore averages and error responses. Tests check recorded response keys against every reached schema. See the [client handoff](../api-client-handoff-0.4.2.md). |

This patch changes documentation, supporting tests and release version metadata.
It adds no migration and changes no application runtime logic, permission, accepted
input or deployment requirement. A generated client may need regeneration to handle
fractional chore averages and the documented error responses. The server already
returns those values.

Issue 944 remains open for its runtime investigation. This release documents only the
existing worker-registration 400 for a NUL in a capability document. The current
calendar error-title disclosure assessment also remains separate. Neither investigation
is resolved by adding its current response to the API document.

## Database comparison

To reproduce the measurement taken on 2026-10-15, export the source commit named
above, initialize an isolated database
with its `bin/victual-migrate`, and populate a product purchase of three units through
its `StockService`. Add a chore and three execution rows with 24-hour and 25-hour gaps.
Run the candidate `bin/victual-migrate` twice. Capture schema-only and data-only
`pg_dump` output before, between and after those runs; use `--no-owner --no-privileges`
and `--inserts --column-inserts` for the data dump. Remove only the random `\restrict`
and `\unrestrict` guard lines before comparing. No application row was excluded.

All three normalized schema dumps had SHA-256
`c7957dfefff22f9893eb57850886dde541a67e33324204cf857afaf873ddbb17`.
All three normalized data dumps had SHA-256
`673e6dd70914381baab96dad7e286e7659a3d10c962ae59623bf6b4b7f2af1c9`.
The fixture used PHP 8.5.10 in `localhost/victual:dev` and PostgreSQL 16.15.
The disposable database was removed after capture. This check does not exercise
refusal, backup restoration, production image replacement or real household data.
The older 0.2.0 timestamp-conversion rehearsal was not used as evidence for this upgrade.

## Release conditions

Merge the reviewed PRs in order, retargeting each stacked PR to `master` after its
predecessor merges. Validate the final release commit, update this record with its SHA
and results, and then follow the [signed-tag procedure](README.md#placing-a-tag).
A passing documentation check does not establish that production images boot or that
an upgrade succeeds. No production-readiness claim for 0.5.0 is made by this patch.
