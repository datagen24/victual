# Reader report: #951 application write precision

Baseline: `b728d0d1a2203523155327b89a03716f915b58c4`. Read-only GPT-6 Luna medium report from `/root/043_app_precision_reader`.

## Findings

The barcode lookup path validates a PHP factor, then passes it through `StockService::ExternalBarcodeLookup()` and LessQL over the shared PDO connection. PostgreSQL stores `quantity_unit_conversions.factor` as `DOUBLE PRECISION`; a trigger computes and persists its reciprocal. With PHP `precision=14`, a float can be stringified to a neighboring double after the PHP checks. The database reciprocal then reflects the rounded value, so persisted factor/inverse values can violate the normal-number guarantee even when the PHP-side values passed validation.

Source references at the named baseline: `helpers/BaseBarcodeLookupPlugin.php:235-259`; `services/StockService.php:1369-1377,1484-1528`; `services/DatabaseService.php:170-181,231-244`; `db/pgsql/baseline/01_tables.sql:223-230`; `db/pgsql/baseline/06_triggers_a.sql:274-305,331-365`; `db/pgsql/baseline/03_views_group2.sql:34-35`.

## Existing measured evidence

The report cites #949/#951 recorded measurements using PHP 8.4.25 (`precision=14`) and PostgreSQL 16.15; suites were not rerun. `PHP_FLOAT_MIN` (`2.2250738585072014e-308`) was stored as `2.2250738585072E-308`, a subnormal. The reported accepted factor interval from `PHP_FLOAT_MIN` through +98 ULP stored as bits `0x000ffffffffffffd`. Values from `2^1022 - 79 ULP` through `2^1022` stored as `0x7fd000000000000a`; their inverse stored as subnormal `0x000ffffffffffff6`. Numeric-string input preserved the exact bit pattern in the reported case.

## Compatibility and migration implications

A shared LessQL/PDO binding change may affect other float writes, including stock amounts/prices, product quantities and measurements, barcode values, recipe amounts and factors, shopping-list amounts, and chore amounts. The schema inventory shows potential scope but does not prove every route uses the same write path. A fix changes future persisted values and may change low bits exposed in conversion or booking results. Existing rounded values remain rounded; the original value generally cannot be inferred safely, so evidence does not justify a repair migration. No schema change is indicated.
